## Problem Statement

We had to decide how to implement the database connection. The application needs a way to store, query, update, and delete data permanently. Since the data structure is manageable, the solution should be simple and reliable to implement. It was also important that the implementation remained realistic within the available time frame.

## Decision

The decision was made to implement the database directly with SQLite instead of using SQLAlchemy. This decision was initially proposed by Fynn and then adopted because SQLite was already familiar to us. As a result, we did not have to learn a new concept such as an ORM before starting the implementation. This made the solution easier to understand, faster to implement, and better suited to our current needs.

## Regarded Options

One possible option was to use SQLAlchemy as an ORM. The advantage would have been a stronger abstraction of the database logic and potentially better scalability for more complex data models. However, the disadvantage was that we would first have had to learn the ORM concept and how to use SQLAlchemy properly. For the scope of our application, this would have added extra effort without a clear immediate benefit.

The second option was to use SQLite directly. The main advantage was that we were already familiar with SQLite and could implement the database logic without an additional abstraction layer. This allowed us to start implementation faster and made errors easier to understand and debug. Since the application does not require a complex database architecture, SQLite was considered the more suitable choice.
