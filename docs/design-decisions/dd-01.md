## Problem Statement

The database structure had to clearly and reliably represent the main relationships of the application. These included students, study programmes, modules, course offerings, submissions, requests and exchanges. It was important to avoid unnecessary duplication of data while keeping the model understandable and suitable for the course exchange logic. The structure also needed to support relationships such as 'Modul' to 'Studiengang', as well as the indirect relationship between 'User' and 'Kursangebote'.

## Decision



The decision was made to use a relational and mostly normalized database structure. This structure was initially designed by Fynn. General module data is stored in "Modul", while specific course offerings are stored separately in "Kursangebote". The n relationship between "Modul" and "Studiengang" is implemented through the helper table "Modulkategorie". The relationship between students and courses is represented through "Abgabe" and "Anfrage", while "Tausch" connects a matching request with a matching submission.

## Regarded Options


One considered option was to use a less normalized structure with fewer tables. This would have made the initial implementation slightly simpler, but it would also have caused more redundant data and reduced maintainability. The chosen relational structure requires more tables and joins, but it represents the application logic more clearly and avoids unnecessary duplication.

Another considered aspect was the primary key of the "User" table. The attribute "username" was originally intended to be used for login, but it now mainly serves as the primary key. Alternatively, "email" or "matrikelnummer" could also have been used, since they are unique as well. Keeping "username" has no relevant technical disadvantage except for a minimally larger amount of stored data, and it keeps the option open to integrate usernames more strongly again in the future, for example for login.
