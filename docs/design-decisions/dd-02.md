## Problem Statement

We had to decide how to implement the database connection. The application requires a means of storing, querying, updating and deleting data permanently. As the data structure is straightforward, the solution should be simple and reliable. It was also important that the implementation remained realistic within the available timeframe.

## Decision

The decision was made to implement the database directly with SQLite instead of using SQLAlchemy. This approach was initially proposed by Fynn and then adopted because we were already familiar with SQLite. Consequently, we did not have to familiarise ourselves with a new concept, such as an ORM, before commencing implementation. This made the solution easier to understand, faster to implement and better suited to our current needs.

## Regarded Options

Other options considered included using SQLAlchemy as an ORM. The advantages would have been stronger abstraction of the database logic and potentially better scalability for more complex data models. However, we would first have had to learn the ORM concept and how to use SQLAlchemy properly, which would have been a disadvantage. For the scope of our application, this would have required extra effort without providing an obvious immediate benefit.

The second option was to use SQLite directly. The main advantage was that we were already familiar with SQLite, meaning we could implement the database logic without an additional abstraction layer. This enabled us to start implementation more quickly and made errors easier to understand and debug. As the application does not require complex database architecture, SQLite was deemed the more suitable choice.
